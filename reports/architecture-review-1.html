After — one deep module, six thin plug-ins

seam · run(ids, worker, version, budget, process_one)

Hermetic tests drive skipped / na / failed / dead / commit through this one interface — no Docker.

Problem

The envelope — the code where the bugs live — is hand-copied into six worker files and tested only behind the Docker gate; the unit layer pins the trivial pure functions instead.

Solution

One deep module owns the envelope; each worker file keeps its pure logic, model, and upsert, and hands the module a per-item callback. NA-vs-SKIPPED stays with the worker (domain); FAILED-vs-DEAD moves inside (protocol).

Wins

  • locality: retry protocol fixed once
  • leverage: one implementation, six callers
  • test surface lands on the risk
  • forgotten commit() becomes impossible
  • transaction ownership stops leaking (repo.py:9)

3 · Give the status vocabulary — and its disjointness — one home

Worth exploring in-process

workqueue.py:49–51 · finalize.py:38–41 · tests/unit/test_workqueue.py:16 · repo.py (claim :149 / heal :384)

Before — one column, two owners, no union

workqueue

PENDING · RUNNING
UNSETTLED = (…)

finalize

SUCCESS · PARTIAL · DEGRADED · FAILED_STATUS
no SETTLED tuple exported

the invariant lives in a test that rebuilds the settled set by hand — a new settled status added to finalize silently misses it

After — disjoint by construction

the status column's value-set, one module

UNSETTLED = (pending, running)
SETTLED = (success, partial, degraded, failed)
assert disjoint at import — or one enum

Claim (repo.py:149) and heal (repo.py:384) both select from tuples the same module exports. The test stops re-deriving the set.

Problem

Two modules jointly own one column's value-set; the load-bearing disjointness invariant has no owner in production code.

Solution

Smallest move: finalize exports SETTLED, and one module asserts disjointness at import. Larger move: one vocabulary module for the whole lifecycle.

Wins

  • locality: the invariant gets an owner
  • new statuses can't dodge the check
  • test asserts, no longer re-derives
Touches a documented decision — work-queue.md assigns each half an owner deliberately. The split can stand; it's the union that needs a home.

The guard still runs inside the adapter's fetch path — the documented rule holds; the loop just stops being copy-me knowledge.

Problem

The SSRF module's core invariant — re-guard every hop, never let the client follow — is implemented in the adapter, so every future fetching adapter must re-remember it.

Solution

Extract the hop-loop into politeness as a driver the adapter hands its single-hop fetch to. The invariant gets one implementation and one test surface.

Wins

  • locality: safety rule, one module
  • next adapter can't forget it
  • chain tests move beside the guard
Honest caveat: today exactly one adapter fetches — one consumer makes this seam hypothetical. It turns real the day the tracker scanner's real adapter lands. Safety-invariant homing is the argument for doing it early anyway.

After — one rig, five plugs

enrich_flow word_count requeue discovery scrape_url

Per-file variation (batch size, fetcher flavour) becomes keyword arguments — the design question is which knobs the rig's interface exposes.

Problem

Every flow test hand-builds the same four-part wiring behind the deps seam; the duplication is test-setup complexity revealing a missing module.

Solution

One conftest rig — a deep test-harness module whose interface is "an installed pipeline", with the variations as parameters.

Wins

  • leverage: one rig, every flow test
  • a new flow test costs one line
  • locator's cost paid once, not five times

Observed, not carded

  • repo/view read split (repo.py owns counts, view.py owns v_enriched reads) — a deliberate cycle-break, and sound; the bounce it costs readers is real but the alternative is worse.
  • Two ports front a raise (scanner, classifier) — fake-by-default is a documented trade-off, and the fakes are genuine adapters exercised at the seam constantly. The seam is earning its keep as a test seam today.
  • repo.py / source.py have zero fast tests — testcontainers is the accepted approach here; candidates 1 and 5 shrink what's hostage to the Docker gate rather than fighting the approach.

Top recommendation

Candidate 1 — the worker run module

It is where depth is cheapest and pays most: one implementation replaces six hand-copies of the retry/ledger/commit protocol, the test surface finally lands on the code that carries the risk, and it makes candidates 2 (post_metadata becomes a plain worker) and 6 (simpler rigs) smaller. Nothing in the trade-offs ledger stands in its way — one file per worker survives intact.
