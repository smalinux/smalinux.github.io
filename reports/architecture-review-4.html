The URL scrape worker — what is good, and what to fix

This looks at the last two code commits. They add a worker that opens each post's web page, downloads it once, and saves it. Most of the new code is good. This page lists a few things that are hard to test, and how to make them easier. It uses easy words. Hard words are explained in the box below.

Words I use in this page

Pure function
A function that uses only its inputs. It does not touch the database or the internet. It is easy and fast to test.
Effect / side effect
Code that changes the outside world — writes to the database, opens a web page.
Fake
A small pretend version of a real thing (like a fake web fetcher), used in tests so you do not need the internet.
Branch
One path in the code — an if case. "7 branches" means the code can go 7 different ways.
Raise
When code throws an error to stop and say "something failed".
Ledger / retry budget
The record of tries per item. After N failed tries the item is marked dead and is not tried again.

The main problem in one picture

The small helper functions have many tests. But bugs do not live there. The important code — the code that decides the result and writes to the database — has few tests, because you need a real database to run it.

HAS MANY TESTS · but not important

check if a URL is safe to fetch
read text out of a web page
count words / cut the text short

These are pure and simple. Good tests — but no result is decided here.

FEW TESTS · but very important

the function _settle — 7 ways:
 • no URL → skip
 • bad URL → skip ✗ no test
 • nothing came back → error ✗ no test
 • blocked by robots → save + skip
 • fetch error → error
 • page code ≥ 400 → error ✗ no test
 • all good → save + ok

To run any of these 7 ways you need a real database. So 3 of the 7 have no test.

The four main things to fix

Sorted from most useful to least. None of these means "delete the code" — the design is good. They only make the code easier to test.

Fix this first

1. Split "decide" from "save to the database"

File: workers/scrape_url.py — the function _settle

The problem

One function does two jobs at the same time. It decides the result (7 different ways), and it also writes the page to the database inside some of those ways. Because writing needs a real database, you can only run this function with Docker. So 3 of the 7 ways are never tested.

The fix

Cut it into two parts. Part one only decides and gives back a small answer: "save this", or "skip, reason X", or "this failed". This part is pure — no database. Part two is 3 lines that read the answer and do the save. Now you can test all 7 ways fast, with no database.

Why it helps

  • The hard, important code finally gets easy tests.
  • The 3 untested ways become tested.
  • It also makes fixes 2 and 4 below easy, because they touch the same place.

NOW — decide and save mixed

_settle(database, …)
  if blocked: save(database); return skip
  if error: raise
  save(database); return ok

Needs a real database to run any line.

AFTER — decide, then save

decide(item, result) → answer (pure, no database)
save(database, answer) (3 lines)

All 7 ways testable with no database.

Important

2. Make it impossible to break the retry counter

File: worker_run.py

The problem

The loop counts a failed try only when a worker raises an error. That is the rule. But the return type also lets a worker return the word "failed". If someone does that, the counter stays at 1 for ever. The item is never marked dead, and the retry limit stops working — quietly. Right now the rule lives only in a comment, so it is easy to break.

The fix

Make the return type allow only the "settled" words: ok, na, skipped. To fail, you must raise. Now a worker cannot return "failed", so this mistake is impossible — the type stops it.

Why it helps

  • The next person who writes a worker is safe by default.
  • No need to read a comment to get it right.
now:   any word (even "failed")
after: only "ok" / "na" / "skipped"
Important

3. Test the web-fetch child — it has zero tests today

File: crawl.py — the child that really opens web pages

The problem

The real web fetch runs in a small separate program (a "child"). That child code has no tests. The riskiest part is this choice: when a fetch fails, was it blocked by robots.txt (so skip for ever) or a normal error (so try again)? This choice is never tested. The bigger tests use a fake fetcher that already knows the answer — so they test the reader, not the real chooser.

The fix

Pull out one small step: "turn a web response into a result". Test it with a fake response — no internet needed. This covers the blocked-vs-error choice.

Why it helps

  • The most risky code stops being a blind spot.
  • You catch a wrong "blocked vs error" choice before it ships.
  • No internet needed in the test.
Good to fix

4. Decide "is this URL OK to fetch?" only once

File: workers/scrape_url.py — the check runs in two places

The problem

The same question — "should we fetch this URL?" — is asked in two places. One place uses it to pick which URLs to fetch. The other uses it to mark an item as skipped. Both must give the same answer. If they ever differ, the item breaks. Today they agree because it is the same function, but nothing keeps them in step, and there is no test for the difference.

The fix

Decide once, save the answer, and read that saved answer in the second place. One decision, one place to test.

Why it helps

  • The two places can never drift apart.
  • One clear place to test the rule.

Smaller notes

5. run_worker is very thin

It is a 3-line wrapper. Fine to keep for now. Just do not let it grow into a copy of the bigger loop next to it.

6. The fetch result holds three shapes in one

"Good page", "blocked", and "failed" all share one type where every field is optional. You can build a nonsense mix by mistake. A clearer type with three separate shapes would help — but it costs some work. Try it together with fix 1.

7. NUL cleaning is spread over 6 spots

Some text fields are cleaned of bad bytes, but two (published, language) are not. Clean once, in one place, so no field is missed. (Your own old SMA note asked about this.)

8. Done already ✓

The helper functions that only the tests used are now private (_url_guard, _extract_page, _count_words, _first_words, _scrapy_settings). This answers your SMA: local function? notes. See the new Code style doc page.

What to do first

Start with fix 1 (split "decide" from "save"). It gives the most value: the hard code finally gets easy tests, and 3 untested paths become tested. After that, fix 2 (the safe return type) and fix 6 (the clearer result type) are small and touch the same spot, so they come almost for free. Then fix 3 to test the web-fetch child.
