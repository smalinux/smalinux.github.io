1 · The stored-page read-back belongs to the table's owner

Strong

word_count.py:67 · ai_class.py:72 (byte-identical) · has_source_code.py:89 (the html+text sibling) · scrape_url.py (owns EnrScrape)

The problem, in plain words. Three shared-fetch workers read back the page that scrape_url stored. Each keeps its own private copy of that read. Two of the copies are byte-identical:

# word_count.py:67 AND ai_class.py:72 — the same function, twice
def _stored_texts(session: Session, ids: list[int]) -> dict[int, str]:
    rows = session.execute(select(EnrScrape.id, EnrScrape.text).where(EnrScrape.id.in_(ids))).all()
    return {row.id: row.text for row in rows if row.text is not None}

Solution

Move the two read-backs into scrape_url.py as stored_texts/stored_pages — the three consumers already import EnrScrape from there, so no new dependency edge appears.

Wins

  • locality: the read lives next to the schema
  • leverage: one implementation, three callers
  • a column change touches one file, not three

Cost

Near zero — the seam already exists (the EnrScrape import); only the functions move across it.

3 · Answer your own comment in source.py

Worth exploring

source.py — the 8-column projection appears 4× (:62, :76, :90, :104); your "I don't like pure sql here" note appears 7×

The problem, in plain words. Your own inline note says the raw SQL is "not clean, nor maintainable". The re-walk's honest finding: the SQL itself is fine — it is a read-only view of a foreign table, kept behind the SourceItem boundary. What is genuinely unmaintainable is that the same 8-column projection is pasted four times, differing only in the WHERE clause. Change one column, edit four strings.

Before — the projection pasted into every query

SELECT id, type, url, "by", "time", fetched_at, title, text
WHERE id > :after … (_FETCH_AFTER)
SELECT id, type, url, "by", "time", fetched_at, title, text
WHERE id < :before … (_FETCH_BEFORE)
SELECT id, type, url, "by", "time", fetched_at, title, text
WHERE … floored (_FETCH_BEFORE_FLOORED)
SELECT id, type, url, "by", "time", fetched_at, title, text
WHERE id = ANY(:ids) (_GET_ITEMS)

After — one projection, four thin predicates

_COLUMNS — the projection, once

id, type, url, "by", "time", fetched_at, raw->>'title', raw->>'text'

WHERE id > :after WHERE id < :before WHERE … floored WHERE id = ANY(:ids)

Plus: the 7 copies of the complaint comment collapse into one honest sentence.

The bigger option — a typed SQLAlchemy Table for items — is possible but speculative: it would declare the scraper's schema inside enrich, the exact coupling SourceItem exists to prevent. The docs call this module deep for that reason. The fragment answers the maintainability complaint with zero new coupling.

5 · A generic worker upsert

Speculative

_upsert_page · _upsert_activity · _upsert_scan · _upsert_count · _upsert_verdict · _upsert_detection — six copies of one ceremony

The problem, in plain words. Every worker's private upsert is the same conflict-resolution ceremony over a different table:

# the skeleton, six times with different columns
stmt = pg_insert(Model).values(id=item_id, version=VERSION, ...columns...)
stmt = stmt.on_conflict_do_update(
    index_elements=[Model.id],
    set_={"version": stmt.excluded.version, ...same columns again...},
)
session.execute(stmt)

The possible move

One upsert_signal(session, model, item_id, version, **columns) that derives the set_ dict from the payload keys — six ceremonies become six one-liners.

Why it stays speculative

It pushes against a documented decision: one file per worker owns everything, including its upsert. The ceremony is also what a new contributor copies when adding a worker — it is boring on purpose. Land this only if a seventh worker makes the skeleton itself the thing being copy-pasted wrongly.
