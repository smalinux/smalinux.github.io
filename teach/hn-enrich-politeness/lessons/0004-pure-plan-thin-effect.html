Pure plan, thin effect

Lesson 0004 · how limits.py and teardown.py split the same way — decide in pure code, act in a thin injected shell

The win You can take any operator command — apply a limit, drop a schema, finalize an item — and split it the way this codebase does: a pure function that decides and returns a verdict as plain data, wrapped by a thin shell that acts through an injected effect. Then you can test the whole decision with zero infrastructure. This is the move behind the two most dangerous commands in the repo.

Two modules, one split

limits.py registers global concurrency caps. teardown.py drops the enrich schema. One is routine, one is destructive — but read their docstrings and they describe the same shape. teardown says it "splits the same way limits does." Here is that shape, named:

limits.pyteardown.py
Pure part — decides plan_limits + reprocess_bounded_below_live plan_teardown (+ redact_dsn, looks_like_prod)
Returns a verdict of… list[LimitSpec] + a bool TeardownPlan(dsn_display, proceed, reason)
Thin part — acts apply_limits / deploy_init destroy_enrich / main
The effect is injected as… upsert= drop=, emit=

Name the pattern — Functional Core, Imperative Shell

Gary Bernhardt's name for it. The core is pure: it takes plain values, returns plain values, touches nothing outside itself — no database, no Prefect, no clock. The shell is imperative and kept as thin as it can be: it calls the core to get a decision, then performs the one effect the decision calls for. The rule of thumb: the interesting logic is all in the core; the shell is too boring to have bugs.

See it in the destructive one

Here is the alternative this codebase rejected — deciding and dropping welded into one function: 

# BEFORE — decision welded to effect. How do you test the prod-guard?
def destroy_enrich(settings, confirm, allow_prod):
    dsn = settings.enrich_db_dsn
    if looks_like_prod(dsn) and allow_prod != "yes":
        print("refusing: prod"); return 0
    if confirm != "yes":
        print("refusing"); return 0
    downgrade_to_base(dsn)     # ← to check "does it refuse prod?" you must risk THIS
    print("dropped"); return 0

To unit-test "does it refuse a production DSN?" you would have to either mock the drop or actually drop a schema. The decision is invisible except by its effect. Now the real code — the decision lifted out into a pure, total function that returns its verdict: 

def plan_teardown(dsn: str, *, confirm: str, allow_prod: str) -> TeardownPlan:
    display = redact_dsn(dsn)
    if looks_like_prod(dsn) and allow_prod != _YES:
        return TeardownPlan(display, proceed=False, reason="refusing: DSN looks like production; ...")
    if confirm != _YES:
        return TeardownPlan(display, proceed=False, reason="refusing: set CONFIRM=yes ...")
    return TeardownPlan(display, proceed=True, reason="dropping the enrich schema ...")

def destroy_enrich(settings, *, confirm, allow_prod, drop=downgrade_to_base, emit=print) -> int:
    plan = plan_teardown(settings.enrich_db_dsn, confirm=confirm, allow_prod=allow_prod)
    emit(f"target enrich DB: {plan.dsn_display}")   # echo BEFORE acting
    emit(plan.reason)
    if not plan.proceed:
        return 0                                     # a refusal is exit 0, not an error
    drop(settings.enrich_db_dsn)                      # the one effect — injected
    emit("enrich schema dropped")
    return 0
src/hn_enrich/teardown.py:105–120

Look at what plan_teardown gives you: a proceed bool and an exact reason string, from plain inputs, with no side effects. A test asserts on the verdict directly — "prod DSN, no override → proceed is False" — and never touches a database. The shell, destroy_enrich, has almost nothing left to get wrong: get the plan, echo it, and if proceed, call the injected drop.

Two properties worth their own names

Total. plan_teardown returns a verdict for every input — there is no path that forgets to answer, and the default answer is refuse. A guard that is total cannot be slipped past by an input its author did not picture.

Safe by default, and ordered. The production check runs first — a prod-looking DSN is refused even with confirm set. Order is policy, and because the policy is pure data-in/data-out, a test pins the order without any infrastructure. (Same instinct as the fail-closed SSRF guard in lesson 0002.)

The same split, in the routine one

limits.py does it too. The invariant is pure:

def reprocess_bounded_below_live(specs: list[LimitSpec]) -> bool:
    by_tag = {spec.tag: spec.limit for spec in specs}
    return by_tag[REPROCESS] < by_tag[LIVE_FETCH]

And the shell enforces it before touching Prefect, acting through the injected upsert:

def deploy_init(settings, *, upsert=_prefect_upsert) -> list[LimitSpec]:
    specs = plan_limits(settings)
    if not reprocess_bounded_below_live(specs):
        raise ValueError("reprocess cap must stay below the live-fetch cap ...")
    apply_limits(specs, upsert=upsert)   # the effect — injected
    return specs

A misconfigured .env is caught by the pure invariant, before a single write reaches the server. And because upsert= is injected, the test for "does it refuse a self-starving config?" drives a fake recorder and never opens a Prefect connection.

Which side of the line?

This is the skill — retrieve it. For each responsibility, does it belong in the pure core (it only decides / computes a value) or the thin shell (it performs an effect on the outside world)?

Decide that reprocess must stay below live-fetch.

Core. reprocess_bounded_below_live — specs in, bool out, nothing touched. The whole "re-runs never starve fresh enrichment" invariant lives here, testable with a literal list.

Compute the refusal message ("set CONFIRM=yes …").

Core — the subtle one. Deciding what to say is part of the verdict: reason is a field on TeardownPlan. Note the contrast with printing it, two rows down.

Mask the password in a DSN string.

Core. redact_dsn is a string-to-string transform — deterministic, no I/O. That is why the redacted DSN can be part of the plan and echoed safely.

Register the limit with Prefect's server.

Shell. _prefect_upsert — a network call to an external server. It is injected as upsert= precisely so the core, and the tests, never reach it.

Drop the enrich schema.

Shell — the whole reason for the split. The destructive act is injected as drop=; a test passes a fake recorder and asserts it was (or was not) called.

Print the target DSN to the operator.

Shell. Writing to stdout is an effect, injected as emit=. Deciding the text was core (two rows up); saying it is shell. That seam is the whole lesson in one pair.

Why the seam types keep recurring

You have now seen the same injected-effect seam four times, each a Callable alias with a real default: 

  politeness.py   Resolver     = Callable[[str], Sequence[str]]    default_resolve
  politeness.py   GateFactory  = Callable[[], ConcurrencyGate]     _open_gate
  limits.py       UpsertLimit  = Callable[[str, int], None]        _prefect_upsert
  teardown.py     DropSchema   = Callable[[str], None]             downgrade_to_base
  teardown.py     Emit         = Callable[[str], None]             print

Every one is dependency injection (lesson 0001's gate, lesson 0003's fake fetcher — same move). The pattern of this lesson tells you where to put those seams: at the boundary between the core that decided and the shell that acts. The verdict crosses that boundary as plain data; the effect crosses it as an injected function.

The transferable lesson

Keep this

When you write a command that does something risky, first ask what it decides. Lift that decision into a pure, total function that returns the verdict as plain data — proceed or not, and why. Leave the shell with just three jobs: get the verdict, perform the one injected effect, report. You will find the hard logic is now testable with literals, and the part that touches the world is too small to hide a bug. For a destructive command, that is the difference between a guard you trust and one you hope about.

Read this next

Gary Bernhardt, Boundaries (SCNA 2012) — the talk that named this. It argues for passing plain values across the boundaries between subsystems (exactly what TeardownPlan and LimitSpec are) and shows why a functional core needs few or no test doubles. Watch it, then look again at plan_teardown: the reason it needs no mocks is the reason the talk is about.
