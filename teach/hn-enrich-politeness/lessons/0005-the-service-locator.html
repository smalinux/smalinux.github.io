The service locator, and its safe default

Lesson 0005 · deps.py — the one place adapters are chosen, why it is a locator at all, and why the default is the fake

The win You can name the seam every worker reaches through — a Service Locator — say honestly why it is here despite being "a step down," and read the one decision that makes it safe: an unbuilt adapter resolves to its fake unless you ask for the real one by name. That last rule is an audit-shaped call, exactly the kind the v5 rebuild must re-apply.

Why a locator at all

Every other seam in this course was passed in as an argument (the gate, the resolver, the inner fetcher). deps is different, and it says why in its own docstring: 

Once the workers are Prefect tasks their parameters are serialized to the
orchestrator's API, so a task can only take item ids — it cannot be handed a
fetcher. Everything a task needs beyond its ids is resolved here instead ...
This is a service locator, and an honest step down from constructor injection.
src/hn_enrich/deps.py:4–11

That is the whole justification. A Prefect task is called by the orchestrator, which can only serialize plain values across its API — you cannot hand a task a live HttpFetcher object. So the task takes item ids, and reaches for its fetcher through a global lookup. Every accessor goes through one tiny resolver: 

def _resolve[T](name: str, build: Callable[[], T]) -> T:
    if name in _overrides:            # a test's fake wins
        return cast(T, _overrides[name])
    if name not in _cache:            # else build the real one once
        _cache[name] = build()
    return cast(T, _cache[name])
src/hn_enrich/deps.py:77–82

Name the pattern — Service Locator (and why "a step down")

A Service Locator is a global registry you ask for a dependency by name, instead of receiving it through your constructor. It is widely called an anti-pattern, and for a real reason: it hides what a piece of code needs. A worker's signature says "give me an id"; nothing in its type tells you it also reaches for a fetcher, a scanner, and a classifier. With constructor injection those needs are visible in the signature; with a locator they are discovered by reading the body.

Why this codebase accepts the trade anyway

The docstring does not pretend otherwise — it calls the locator "an honest step down." The trade is forced by Prefect (tasks take serializable ids), and it is bounded on purpose: the module is kept small, and — its words — "pure logic never comes through here." The locator holds only the impure, outside-world adapters. Everything you learned to test with literals (lesson 0004's cores) stays out of it, so the locator's hidden-dependency cost never touches the code where it would hurt most.

The override seam contains the global state

A global registry is mutable global state — the thing tests fear most. The override context manager is what makes it safe: it snapshots what was there, installs the fakes, and restores on exit, so no test can leak into the next: 

with deps.override(fetcher=FakeFetcher(...), scanner=FakeScanner(...)):
    ...        # inside: the fakes win, for this block only
# outside: whatever was there before is back, cache included
deps.override — src/hn_enrich/deps.py:165–199

It even snapshots the cache, not just the overrides: a dependency built inside the block (from an overridden setting, say) is dropped on exit, so nothing assembled from a test's replacements outlives the test. This is the "only sanctioned way to put a fake behind the accessors" — the single seam that buys back the testability a locator would otherwise cost you.

The decision worth the lesson — the default is the fake

Two adapters are not built yet: the tracker scanner and the AI classifier. Their real implementations raise. So the module inverts what you might expect — it selects the real one only on an explicit, by-name opt-in: 

def _build_scanner() -> TrackerScanner:
    if not cfg.use_real_tracker_scanner:
        return FakeScanner(default=ScanResult(n_ads=0, n_trackers=0))   # default
    inner = TrackerRadarScanner(timeout_s=cfg.fetch_timeout_s)          # opt-in only
    return PolitenessScanner(inner, limiter=_rate_limiter(), gate=live_fetch_gate)
src/hn_enrich/deps.py:125–130

Read the reasoning straight from config, because it is the whole point:

The opt-ins for the two adapters that are not built yet. Both real
implementations raise, so selecting one marks every item it touches failed,
and then dead, for as long as the run lasts. They are therefore off by
default ... reaching for an unbuilt adapter has to be something you asked for
by name, not something a live run discovers on your behalf a few thousand
dead-letters in.
src/hn_enrich/config.py:91–96

This is safe by default again — the same instinct as the fail-closed SSRF guard (0002) and plan_teardown refusing unless confirmed (0004). The dangerous thing (an adapter that raises) must be requested, never defaulted into. And note the sharp corollary, quoted in the module: "an API key alone selects nothing." A configured anthropic_api_key does not turn the real classifier on — only use_real_ai_classifier does. A credential is not consent.

Real or fake?

Retrieve the selection rules. For each call, does the accessor hand back the fake or the real adapter? Decide from the use_real_* flags and the override seam — not from whether a key or a class exists.

deps.scanner() with a default .env (no flags set).

Fake. use_real_tracker_scanner defaults False, so FakeScanner serves a zero count and touches no browser.

deps.classifier() with anthropic_api_key set but use_real_ai_classifier unset.

Fake — the trap. A key alone selects nothing; without the explicit opt-in you still get FakeClassifier. A credential is not consent.

deps.fetcher() in production, no overrides.

Real. The contrast that proves the rule: the fetcher is built (real HttpxFetcher, politeness-wrapped), so there is no use_real_fetcher flag and no fake default. Only the two unbuilt adapters default to fake.

deps.scanner() inside with deps.override(scanner=my_fake).

Fake — my_fake, specifically. An installed override wins over both cache and build (_resolve checks _overrides first), for the length of the block only.

deps.classifier() with use_real_ai_classifier=yes and a key set.

Real — ClaudeClassifier. Flag set and key present is the one path to the real one. (Flag set but key missing is refused loudly right here, before any item is touched — not returned.)

The transferable lesson

Keep this

A locator or registry is sometimes forced on you (here, by the orchestrator). When it is, pay the two tolls that keep it honest: give it one seam to install fakes (so tests stay isolated), and make every risky selection opt-in, not default (so a live run cannot stumble into the dangerous path). The failure this design refuses is quiet: a raising stub reached by default would bury the corpus in dead-letters at worker speed, and CI would never see it because CI injects the fakes. Safe-by-default is how you make sure the person who pays for a mistake is the one who typed the opt-in.

Read this next

Mark Seemann, "Service Locator is an Anti-Pattern" — the canonical case against the pattern this module uses. Read it as the prosecution: Seemann's core charge is that a locator hides a class's dependencies. Then judge whether deps.py answers the charge — it concedes the point in its own docstring, confines the locator to impure adapters, and keeps pure logic out. Deciding whether that is enough is exactly the design judgment your rebuild needs.

Push on: constructor injection was "a step up" — so what, concretely, would the workers' signatures look like if Prefect could pass objects, and is the locator hiding anything a reader genuinely needs? And a callback: the fetcher is always real — does that make it harder to test a worker than the scanner, or does override flatten the difference?
