The edge of the guard

Lesson 0002 · what politeness.py structurally cannot do — and why that answers "buy or build"

The win Lesson 0001 was about what a boundary lets a module do. This one is the other half: a boundary also fixes what a module cannot do. By the end you can look at the SSRF guard, name the one gap it cannot close, and say why the fix is an egress proxy rather than more Python — which is exactly the call already on this project's decision record.

Start from what the guard does right

The guard is good. Before any hop is fetched, it resolves the hostname and refuses if any address it points at is non-public — and it does this for every redirect hop, not just the first. That is the loop in walk_redirects: 

for _ in range(max_redirects + 1):
    assert_public_url(hop, resolve=resolve)   # resolve #1 — to JUDGE
    result = fetch_once(hop)                   # ...then hand the url onward
    if result.next_url is None:
        return result.response
    hop = result.next_url
src/hn_enrich/politeness.py:176–181

Nothing here is wrong. This is the OWASP guidance made executable. So the gap is not a bug in the guard — it is the edge of it. To see the edge, follow the url one step further, into the adapter that actually fetches it.

The url is handed on — not the address

assert_public_url resolved the hostname to judge it. But look at what it passes to fetch_once: the url string, hop — not the address it just validated. So the transport has to resolve the very same name a second time to open its connection: 

def fetch_once(hop: str) -> Hop[httpx.Response]:
    response = client.get(hop)   # resolve #2 — httpx resolves the host to CONNECT
    ...
src/hn_enrich/adapters.py:104–110

Two independent DNS lookups of the same hostname, for a single hop. The guard did one, to decide may I. httpx does another, to decide where to send the packet. They are not the same lookup — the guard's resolver is even injectable (resolve=), while httpx uses its own. Nothing guarantees the two answers match.

Name the pattern — check-then-use (TOCTOU)

This shape is old and has a name: time-of-check to time-of-use. You check a thing, and then you use it — and between the two moments the thing can change, so the check no longer describes what you used. When the "thing" is a DNS name, the attack that exploits the window has its own name: DNS rebinding. OWASP flags it directly on the page this module implements.

The attack, on a timeline

The attacker controls the name evil.example and its DNS server, set to a very short TTL so answers are never cached: 

  time ──────────────────────────────────────────────────────────▶

  guard: assert_public_url("http://evil.example/")
            │  resolve #1  ─────▶  DNS answers 203.0.113.9   (public ✓)
            │                                    guard says: allowed
            │
            │   ← attacker flips the DNS record to 169.254.169.254 →
            │
  httpx: client.get("http://evil.example/")
            │  resolve #2  ─────▶  DNS answers 169.254.169.254 (cloud metadata!)
            └────────────────────▶  connects there, fetches secrets

                 ▲                          ▲
              CHECK                        USE
            (public)                   (internal)
                 └──── the window the guard cannot see ────┘

169.254.169.254 is the cloud metadata endpoint — credentials live behind it. The guard did everything right and still lost, because the address it approved is not the address httpx dialed. The guard's power ends at the edge of the process; the resolution that matters happens just past it.

Why no amount of Python closes this

The instinct is to patch it in place. Retrieve, don't guess — for each proposed fix, does it actually shut the window, or only shrink it? Answer from the timeline, not from hope.

Call assert_public_url a second time, right before client.get.

Stays open. You have moved the check closer to the use, not joined them. There is still a gap between your second check and httpx's own resolve — and rebinding with a short TTL flips the answer inside any gap, however small.

Cache the guard's resolved address and reuse it for the connection.

Stays open — as written. Good instinct, wrong wiring: httpx does not read your cache. Unless the validated address is what actually gets dialed, httpx resolves again and the cache changes nothing. (Make it the dialed address and you have the next option.)

Resolve once, then tell the transport to connect to that exact IP (IP pinning).

Closes it — this is the real in-process mitigation: the checked address is the used address, so there is no second lookup to poison. But note what it cost: you are now overriding the transport's connection layer (and juggling TLS SNI and the Host header by hand). You have started building a proxy inside your process. Better to build it once, at the boundary.

Route all egress through Smokescreen, which resolves and validates at connect time.

Closes it. The proxy's validation and the proxy's connection use the same resolution, by construction — check and use collapse into one moment. This is IP pinning done properly, in one place every worker shares, instead of re-derived in each adapter.

Add network egress rules that drop packets to private and CGNAT ranges.

Closes it — at a lower layer. This does not care about names or timing at all: even if every check above is bypassed, the packet to an internal address never leaves the host. It is the last line, and it catches what a hostname-level control structurally cannot (see the CGNAT note below).

See the pattern in the answers. Every fix that stays inside the process making the request can only shrink the window — because there are always two moments, check and use, with a seam between them. The fixes that close it do one of two things: make the checked address be the connected one (pin it, or proxy it), or drop the packet at a layer that never trusted the name in the first place (the network). The boundary of politeness.py is the process boundary, and this gap lives on the far side of it.

So the decision was infrastructure, not code

This is why politeness.py is frozen and the real fetch path waits on Smokescreen plus egress rules, rather than on a cleverer guard. It is not that the guard is unfinished — it is that the last gap is unreachable from where the guard stands. The two closing moves from the quiz are exactly the two halves of the plan:

LayerClosesCannot close
politeness.py guard + walk_redirects Public-looking name → private IP, at check time; every redirect hop. The check-then-use window: the name can flip before httpx connects.
Smokescreen (egress proxy) The window — validation and connection share one resolution. A client that bypasses the hostname ACL with a raw IP; CGNAT ranges. Its ACL acts on "hostnames as they appear in the request."
Network egress rules (firewall) Whatever slips the layers above — at the packet level, by IP range. Nothing above it; it is the floor. (But it is blunt — no per-request context.)

That middle row is your open CGNAT gap in one sentence: Smokescreen validates the name it is handed, so an address in the carrier-grade NAT range (100.64.0.0/10) that never went through a name still needs the firewall row to stop it. No single layer is enough; that is why the decision names both the proxy and the egress rules. Defense in depth is not belt-and-braces caution here — it is forced by the fact that each layer has an edge the next one covers.

The transferable lesson

You came here to rebuild v5 with the boundaries right. Here is the rule this lesson buys you, good far beyond SSRF:

Keep this

When a requirement lands, ask not only "which module owns it?" (lesson 0001) but "can a module at this layer even reach it?" If the honest answer is no — the thing you must control happens on the far side of your boundary — then the fix is a different layer, not more code at this one. Recognising that early is what stops you from writing a guard that feels airtight and quietly is not. The dangerous version of this bug is the one that leaves no witness: it passes every test, because the tests, like the guard, never see the second resolution.
