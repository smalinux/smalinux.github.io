Mixed retrieval

Lesson 0006 · no new pattern — retrieve all five, cold, in shuffled order

The win This lesson teaches nothing new. That is the point. You have covered five patterns quickly, and quick coverage builds fluency — the feeling of knowing. Retention is different: it comes from pulling each idea out of memory, in mixed order, with no section heading telling you which lesson it is from. That is what this page makes you do.

Two ideas from how people actually learn, both Robert Bjork's "desirable difficulties": interleaving (mix topics, don't block them) and retrieval practice (recall beats re-reading). The questions below are deliberately shuffled across lessons and deliberately a little hard. If one makes you pause and reconstruct the reasoning — good. That pause is the learning.

Part 1 — Free recall (the hard, useful kind)

Read each prompt, answer it out loud or on paper first, and only then open the card to check. Producing the answer from nothing is worth ten times re-reading it. Some of these need two lessons at once.

Name the pattern: PolitenessFetcher both is and has an HttpFetcher. And name the one thing it must do to be worth its layer. 0003

Decorator over a Port. Is-a and has-a at the same interface is the Decorator signature; the interface is the HttpFetcher Port.

It must add real behaviour — guard, space, gate — not just forward the call. A wrapper that only forwards is a pass-through, which Ousterhout counts as a red flag: a layer with no new abstraction, pure cost.

The SSRF guard resolves and judges every hop, yet a gap survives. Name the gap — and name the safety property the guard shares with plan_teardown. 0002 + 0004

The gap is check-then-use (TOCTOU), exploited by DNS rebinding: the guard resolves to judge, then httpx resolves again to connect, and the answer can change between. It lives below the process boundary, so no in-process code closes it — hence the egress proxy.

Shared property: fail-closed / safe by default (and total). The guard refuses on any doubt; plan_teardown refuses unless confirm=="yes", prod-checked first. The dangerous path must be asked for, never defaulted into.

In limits.py, where is the decision vs the effect, and which side imports Prefect? 0004 + 0001

Decision (pure core): plan_limits + reprocess_bounded_below_live — specs and a bool, no I/O. Effect (thin shell): apply_limits / deploy_init, acting through the injected upsert.

Only the effect imports Prefect (_prefect_upsert). And by Dependency Inversion, politeness.py owns ConcurrencyGate while limits.py depends on it — so the policy never imports the machinery.

You must test "a worker counts words from a page" with no network. Name the two seams that let you, and the pattern behind each. 0003 + 0005

The HttpFetcher Port — drop in a FakeFetcher with canned pages (Ports & Adapters / Decorator seam).

deps.override(fetcher=...) — install that fake behind the accessor for one with-block (Service Locator seam). The worker never learns the real fetcher exists.

Capstone. New v5 rule: "never fetch a URL on a customer blocklist." Which module, which existing function does it join, and is it core or shell? mission

politeness.py — it is answerable from the url alone (lesson 0001's test), so it is per-call policy, not a system cap.

It joins is_public_url / assert_public_url as one more refusal reason, guarded before the effect inside _politeness. It is a pure predicate — core: url in, allowed/refused out, no I/O. And it should be fail-closed: if the blocklist can't be read, refuse. That is the whole course applied to one new line.
