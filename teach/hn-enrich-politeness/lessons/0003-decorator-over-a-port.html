Why PolitenessFetcher is an HttpFetcher

Lesson 0003 · the Decorator-over-a-Port move, and what it buys you at test time

The win You can look at PolitenessFetcher and name the exact design move — a Decorator over a Port — and say what it buys that the obvious alternative (an if inside the real fetcher) throws away. The payoff is the thing your rebuild lives or dies on: what you can test without touching the network.

Two ways to add politeness to a fetch

The job: before every live fetch, run the SSRF guard, space the domain, hold a gate (lesson 0001). There are two places to put that. Here is the one this codebase did not choose — the policy baked straight into the real transport: 

# BEFORE — the design NOT chosen. Policy tangled into transport.
class HttpxFetcher:
    def fetch(self, url):
        assert_public_url(url)              # guard  ┐
        self._limiter.acquire(host(url))    # space  │ policy, welded to
        with self._gate():                  # gate   ┘ the httpx machinery
            # ... build httpx.Client, walk redirects, parse html ...
illustration — not in the repo

It works. But now the policy and the transport are one lump. To test that the guard refuses 10.0.0.1, you must stand up an httpx client. To reuse the same policy for the tracker scanner, you copy those four lines into a second class — and now they can drift apart. This is a shallow, entangled module, the opposite of what lesson 0001 praised.

Here is what the codebase actually does:

# AFTER — the design chosen. Policy is its own object, same shape as a fetcher.
class PolitenessFetcher:
    """An ``HttpFetcher`` that guards, spaces, and gates before delegating."""

    def __init__(self, inner: HttpFetcher, *, limiter, gate=_open_gate, resolve=default_resolve):
        self._inner = inner            # ← it HOLDS an HttpFetcher
        ...

    def fetch(self, url: str) -> FetchResult:
        with _politeness(url, limiter=self._limiter, gate=self._gate, resolve=self._resolve):
            return self._inner.fetch(url)   # ← ...and DELEGATES to it

Name the pattern — Decorator over a Port

Two facts about PolitenessFetcher together are the whole pattern. It is an HttpFetcher (it has a fetch(url) -> FetchResult method, so it satisfies the port), and it has an HttpFetcher (the inner it wraps). Is-a and has-a, at the same interface — that is the signature of the Decorator pattern. The interface it decorates is a Port (lesson references: the one-method Protocol in ports.py): 

class HttpFetcher(Protocol):
    def fetch(self, url: str) -> FetchResult: ...

Because all three plug into the same socket, anything that wants "a fetcher" takes the port and never knows which one it got. deps hands the wrapped one to production and returns it as the port: 

def _build_fetcher() -> HttpFetcher:
    inner = HttpxFetcher(user_agent=cfg.user_agent, timeout_s=..., max_redirects=...)
    return PolitenessFetcher(inner, limiter=_rate_limiter(), gate=live_fetch_gate)

What the move buys — #1: test each layer alone

Because the seam is a plain interface, you can put a fake on either side of it and test one layer with the other absent:

  • Test the policy, no network. Wrap a FakeFetcher (canned pages) in a PolitenessFetcher, inject a fake resolve= and a fake clock, and you can prove the guard refuses, the limiter spaces, and the gate is held — without httpx ever loading.
  • Test the transport, no policy. HttpxFetcher takes an injectable transport=, so its wire behaviour is tested against a fake transport, with no politeness in the way.
  • Test a worker, neither. A worker asks deps for "a fetcher"; a test swaps in a fake at that seam and the worker runs with no network at all:
with deps.override(fetcher=FakeFetcher({url: FetchResult(text="hi", html="<p>hi</p>", http_status=200)})):
    ...   # the worker under test never learns the real fetcher exists
deps.override — src/hn_enrich/deps.py:165–199

The BEFORE design cannot offer any of these cleanly: with policy welded to httpx, every test of the guard drags the transport along, and there is no seam to slip a fake into.

What the move buys — #2: one policy, two ports, no drift

The tracker scanner does its own live visit, so it needs the exact same politeness. Because politeness is an object, not four lines inside a fetcher, the scanner gets it by the identical move — a Decorator over the TrackerScanner port, running the same _politeness policy: 

class PolitenessScanner:
    """A ``TrackerScanner`` that guards, spaces, and gates before delegating."""

    def scan(self, url: str) -> ScanResult:
        with _politeness(url, limiter=self._limiter, gate=self._gate, resolve=self._resolve):
            return self._inner.scan(url)
src/hn_enrich/politeness.py:258–282

One shared _politeness, two decorators, two ports. The guard, spacing, and gate cannot drift between fetch and scan, because there is only one copy of them. In the BEFORE world those rules would exist twice and someone would eventually fix one and forget the other.

What can you actually test with fakes?

This is the skill, so retrieve it. For each claim: can a unit test check it with fakes — no network, no browser, no Prefect server — or does it need the real world? Decide from where the thing being tested lives relative to the seam.

The SSRF guard refuses a hostname that resolves to a private IP.

Yes. Inject resolve= with a fake that returns 10.0.0.1. No socket opens; the guard's DNS policy is judged without DNS.

PolitenessFetcher waits between two hits on one domain.

Yes. RateLimiter takes an injectable monotonic and sleep; wrap a FakeFetcher and assert the fake clock advanced. No wall-clock wait, no network.

A worker counts the words on a fetched page.

Yes. deps.override(fetcher=FakeFetcher({url: page})) puts a canned page behind the same seam. The worker never learns the real fetcher exists.

The guard stops a DNS flip between the check and the connect.

No — and this is lesson 0002 returning. The rebinding window lives below the seam, in httpx's own resolve. No fake reproduces it in-process; that is precisely why it "leaves no witness" and why the fix was a proxy, not a test.

A real tracker scan finds the trackers on a live site.

No. The real scanner is a deferred stub that raises (adapters.py:155); CI injects FakeScanner, which serves canned counts. A unit test asserts against the fake — never against what nytimes.com actually ships.

The seams on the fetch path, side by side

Three different seams do three different jobs. Do not confuse them:

SeamPatternWhat it lets you swap
HttpFetcher / TrackerScanner (the port) Decorator over a Port Real ⇄ fake ⇄ politeness-wrapped, all at one interface. This lesson.
GateFactory (the gate) Dependency Inversion Open gate ⇄ Prefect's real cap, without politeness importing Prefect. Lesson 0001.
deps.override(...) Service Locator Any dependency, for the length of a with-block. Its own honest trade-off (see the module docstring).
A caution — the pass-through that is not this

A decorator is only worth its layer if it adds something. PolitenessFetcher.fetch does real work — guard, space, gate — before it delegates. A wrapper whose method just forwards the call unchanged is a pass-through, and Ousterhout counts those as a red flag: a new layer with no new abstraction, pure cost. The test is not "does it wrap?" but "does the wrapper earn its keep?" This one does.

The transferable lesson

Keep this

When a rule must run around an external effect — before it, after it, or instead of it — give the rule the same interface as the effect and wrap it, rather than editing the effect. You gain a seam you can put a fake on from either side, and the rule becomes reusable across every effect that shares the interface. "Program to the interface" is the slogan; the Decorator is one of the concrete moves it buys.

Read this next

Ousterhout, A Philosophy of Software Design — the chapters on different layer, different abstraction and pass-through methods. They are the other half of this lesson: a decorator is a new layer, and Ousterhout is strict about when a new layer is justified. Read them and then re-judge PolitenessFetcher yourself — is it a real abstraction, or a pass-through? (You should be able to defend "real" in one sentence.)
