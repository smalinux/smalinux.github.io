Where does a rule live?

Lesson 0001 · politeness.py and limits.py, and the seam between them

The win By the end of this page you can take any new rule about fetching the web and say which of the two modules owns it — and say why, in one sentence. That is the same judgement the v5 rebuild needs, applied to a small case.

Two questions

The two modules look similar from a distance. Both are about "don't hammer the web". Both end up wrapped around the same fetch. But each one answers a different question, and the question is the boundary:

Module The question it answers What it needs to know
politeness.py May this one call go, and when? The url.
limits.py How many calls may run at once, across everything? Two numbers from .env.

Notice that neither can answer the other's question. A single call has no idea how many other calls are in flight — it cannot see them. And a number in .env has no idea what url you are about to visit. That mutual blindness is not a weakness in the design; it is the design.

Everything politeness.py does, in six lines

The whole module funnels into one shared policy. Both wrappers (PolitenessFetcher and PolitenessScanner) run their outward call inside it, so the two cannot drift apart: 

@contextmanager
def _politeness(
    url: str, *, limiter: RateLimiter, gate: GateFactory, resolve: Resolver
) -> Iterator[None]:
    assert_public_url(url, resolve=resolve)         # 1. may I visit at all?
    limiter.acquire(urlsplit(url).hostname or "")   # 2. when may I visit?
    with gate():                                    # 3. is there a free slot?
        yield
src/hn_enrich/politeness.py:226–233 · comments added here

Read the three steps as three different kinds of question. Step 1 and step 2 are answered from the url alone. Step 3 is not — step 3 asks somebody else. And that somebody is where the boundary falls.

Everything limits.py decides, in four lines

def plan_limits(settings: Settings) -> list[LimitSpec]:
    return [
        LimitSpec(LIVE_FETCH, settings.live_fetch_concurrency),
        LimitSpec(REPROCESS, settings.reprocess_concurrency),
    ]
src/hn_enrich/limits.py:102–106

No url. No fetching. No web. Just two names and two numbers — and one rule relating them (reprocess_bounded_below_live), which says re-runs must stay under fresh enrichment so a heal can never starve the live pipeline. This module is about capacity, and capacity is a property of the whole system, never of one call.

The seam: a gate

Step 3 above says with gate():. The gate is the one place the two modules touch, and the way they touch is the interesting part. politeness.py defines what a gate is: 

ConcurrencyGate = AbstractContextManager[None]
GateFactory = Callable[[], ConcurrencyGate]
src/hn_enrich/politeness.py:65–66

That is the entire specification: something you can stand inside. Not how many slots. Not who counts them. Not Prefect. Then limits.py supplies a real one: 

def live_fetch_gate() -> ConcurrencyGate:
    return cast(ConcurrencyGate, concurrency(LIVE_FETCH, strict=True))
src/hn_enrich/limits.py:154–155

Name the pattern — Dependency Inversion

Look at the arrow. The module with the policy (politeness.py) owns the abstraction; the module with the machinery (limits.py, and behind it Prefect) depends on it. You can prove it in one line — limits.py:82 reads from hn_enrich.politeness import ConcurrencyGate, and politeness.py imports nothing from limits.py at all.

This is why politeness.py has no idea Prefect exists, and why its tests never start a server. The naive arrangement — the fetcher reaching into limits.py to ask for the cap — would drag Prefect into every test of the SSRF guard.

The line worth memorising: politeness.py knows there is a gate, but not how wide it is. limits.py knows how wide, but not when you will open it.

Place the rule

Now retrieve it — don't scroll up. For each rule, which module owns it? Answer from the two questions, not from memory of the file.

Refuse a url whose hostname resolves to 10.0.0.5.

politeness.py. Answerable from the url alone — this call, this target. No other call in the system changes the answer.

Never let more than 8 fetches run at once across the whole pipeline.

limits.py. A count across the system. One call cannot see the other seven, so it cannot enforce this — it can only ask for a slot.

Wait 2 seconds between two hits on example.com.

politeness.py. Tempting to call this a "limit", but it needs the url's hostname to mean anything — so it is per-call. That is RateLimiter, step 2.

Re-runs must never crowd out fresh enrichment.

limits.py. A relationship between two capacities — reprocess_bounded_below_live. Nothing about any single url is involved.

Check every hop of a redirect chain before following it.

politeness.py. One call's journey. It lives in walk_redirects — and it lives there rather than in the adapter so that no adapter can forget it. The loop is the rule.

Refuse to run if the cap was never registered on the server.

limits.py. That is strict=True. It is about whether the capacity exists — a fact about the deployment, not about a url.

Name the pattern — Null Object

One case that catches people. The default gate — the one that never blocks — lives in politeness.py, not limits.py: 

def _open_gate() -> ConcurrencyGate:
    # The default gate never blocks; the real cap is injected by a later slice.
    return nullcontext()
src/hn_enrich/politeness.py:217–219

Why there? Because politeness.py has to work with no capacity system at all — that is what "owns the abstraction" means. A do-nothing default keeps every caller and every test free of an if gate is None. The empty gate is not a limit; it is the absence of one, which is politeness's own business.

Where this goes next

A boundary also defines what a module cannot do, and politeness.py has a hard edge worth knowing before you rebuild it. It resolves a hostname, judges the addresses, and then hands the url onward — so whoever fetches it resolves it a second time. Between those two resolutions, the answer can change. That gap has a name, OWASP names it too, and it cannot be closed from inside this module — which is exactly why the decision on record is an egress proxy rather than more code. That is lesson 0002.

Read this next

The primary source for this module is OWASP's Server Side Request Forgery Prevention Cheat Sheet. Read just the "Case 2: Application can send requests to ANY external IP address or domain name" section — perhaps ten minutes. You will recognise three rules you have already seen today, because politeness.py implements them nearly verbatim: disable redirect-following in the client, resolve a name to all its addresses and validate every one, and deny loopback / private / link-local. The module's rules are not house style; they are the standard, made executable.

Anything here that did not land? Ask — that is what your teacher is for. Good questions to push on: why the limiter is shared rather than one per wrapper; why Resolver is injectable at all; or what would actually break if someone put the live-fetch cap inside politeness.py.
