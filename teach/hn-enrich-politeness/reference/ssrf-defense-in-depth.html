SSRF defense-in-depth ladder

Reference · every rung on hn-enrich's live-fetch safety path, what it closes, what it can't · verified 2026-07-17

The one idea

SSRF defense is layered because each control has an edge the next one covers. An in-process guard cannot close the check-then-use window; a hostname proxy cannot stop a raw-IP or CGNAT bypass; the network layer has no per-request context. No single rung is enough — that is not caution, it is the structure of the problem.

The ladder

#RungWhereClosesCannot close
1 follow_redirects=False adapters.py:100 Silent hops: forces every redirect back through the guard instead of the client walking the chain unjudged. Anything about addresses — it only controls who follows the chain.
2 Guard resolves + judges every address (A + AAAA), fails closed politeness.py:100–136 A public-looking name backed by a private / loopback / link-local IP, at check time. The check-then-use window (rung's own resolution ≠ the transport's).
3 walk_redirects guards every hop before fetching it politeness.py:168–185 A public url that redirects to an internal one: the redirect target is judged like any first url. Same window as rung 2 — it guards each hop, but each hop still re-resolves to connect.
4 IP pinning (validated IP handed to the transport) not built — would live in the adapter The window: the checked address is the connected one. Fragile — reimplements the client's connection layer (TLS SNI, Host). Better centralised as a proxy.
5 Egress proxy — Smokescreen infra (decision on record) The window, properly: validation and connection share one resolution, in one place every worker uses. A raw-IP request that skips the hostname ACL; CGNAT. ACL acts on "hostnames as they appear in the request."
6 Network egress rules (firewall): drop RFC1918 + CGNAT 100.64.0.0/10 infra (decision on record) Whatever slips rungs 1–5 — at the packet layer, by IP range. The floor. Nothing below it. But blunt: no per-request or per-hostname context.

Rungs 1–3 are what politeness.py is, and it does them correctly. Rungs 5–6 are what it structurally cannot be, because it runs inside the process making the request. That boundary is the reason the decision on record is infrastructure, not a cleverer guard.

The check-then-use window, precisely

  assert_public_url(hop)   →  resolve #1  →  judged public ✓   (politeness.py:177)
        ── window: the name's DNS answer can change here ──
  client.get(hop)          →  resolve #2  →  connects & fetches (adapters.py:105)

Two independent lookups of one hostname, per hop. The guard's resolver (resolve=, injectable) is not the resolver httpx uses to connect, so even the same system resolver can return different answers across the two — by attacker design (rebinding, short TTL) or by accident (round-robin, TTL expiry). Any fix that leaves two lookups only shrinks the window; closing it means one resolution serves both check and connect (rung 4/5) or the network refuses the packet regardless (rung 6).

Terms

TermIs
Check-then-use (TOCTOU)Validate a thing, then use it, with a gap between where it can change. Here: resolve-to-judge, then resolve-to-connect.
DNS rebindingThe attack that exploits that gap: attacker-controlled name answers public on the first lookup, internal on the second.
IP pinningConnect to the exact address you validated, so there is no second lookup to poison.
Egress proxyA forward proxy all outbound requests go through; validates and connects in one place, so check and use share a resolution.
Defense in depthStacked controls where each covers the edge of the one before. Forced here, not optional.
CGNAT range100.64.0.0/10 (RFC 6598). Not "private" by the RFC1918 test, so a hostname-level control can miss it; the firewall rung catches it.
